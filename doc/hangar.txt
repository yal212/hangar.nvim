1. INTRODUCTION                                                 *hangar-intro*

hangar.nvim spawns headless coding-agent runs — Claude Code (default),
OpenAI Codex, Gemini CLI, or OpenCode — each in its own git worktree and
branch. A live dashboard shows status, cost, and changed files; review a
run's diff, merge the winners, discard the rest, without leaving Neovim.

==============================================================================
2. REQUIREMENTS                                          *hangar-requirements*

- Neovim >= 0.10
- git >= 2.5 (worktree support)
- At least one agent CLI on $PATH (`claude` by default)
- A git repository with at least one commit (runs branch off HEAD)

Run `:checkhealth hangar` to diagnose setup problems; it also reports the
installed plugin version.

Pin a release instead of tracking `main` (lazy.nvim): >lua
    { "yal212/hangar.nvim", version = "^0.2", cmd = "Hangar", opts = {} }
<
While 0.x, |hangar-config| option names and the adapter contract
(|hangar-adapters|) are stable within a minor version; breaking changes
bump the minor. See CHANGELOG.md in the repository.

3. COMMANDS                                                  *hangar-commands*

:Hangar                                                              *:Hangar*
    Open the dashboard (|hangar-dashboard|).

:Hangar spawn [flags] {prompt}                                 *:Hangar-spawn*
    Spawn an agent run in a fresh worktree. Flags come before the prompt:

      --yolo            full tool access (see |hangar-adapters| for the
                        per-adapter mapping)
      --safe            reduced permissions (per-adapter mapping)
      --model {m}       model for this run, e.g. `haiku`
      --adapter {a}     agent CLI: `claude_code`, `codex`, `gemini`,
                        `opencode`
      --n {count}       best-of-N: spawn {count} attempts (1-8) of the same
                        prompt in parallel worktrees; the dashboard groups
                        them, and merging one offers to discard the rest

    Every spawn needs `--yolo` or `--safe` unless `default_permission` is
    set (|hangar-config|) — headless agents can't answer permission prompts.

:Hangar kill {id}                                               *:Hangar-kill*
    Stop a running agent (SIGTERM). Also drops a queued run from the queue
    and signals a detached one. <Tab> completes the ids it accepts.

:Hangar clean                                                  *:Hangar-clean*
    Delete worktrees and branches of all non-running runs and forget them.

4. DASHBOARD                                                *hangar-dashboard*

One row per run: status icon, id, adapter, elapsed, model, turns, cost,
changed files, prompt. A footer totals running/queued counts and cost
across the repo's runs. Updates live. Keys:

  <CR>    open the run's transcript (streaming tail)
  d       review: changed files list; <CR> on a file opens a |diffsplit|
          against the run's base commit
  m       merge the run's branch into your current branch (confirm first);
          for a best-of-N attempt, offers to discard the sibling attempts.
          If the merge fails because the branches conflict or diverged,
          offers to rebase the run branch onto your HEAD (inside its own
          worktree — your tree is never touched) and retry; declining
          leaves everything as it was. Edits a failed, killed or orphaned
          run left uncommitted are committed to its branch first, so the
          merge carries everything `d` showed. A run with no changes is
          refused. Untracked files in your tree do not block a merge
          (git still refuses one that would overwrite them)
  x       discard: delete worktree + branch, forget the run (confirm first)
  i       iterate: prompt for feedback and spawn a follow-up run. Where the
          adapter supports resume (|hangar-adapters|), the follow-up
          continues the agent session in the same worktree — prior edits
          and context carry over, and the superseded run keeps only its
          transcript. Otherwise a fresh run starts with the feedback
          appended to the original prompt. The runs share a group, so the
          dashboard shows the iteration lineage.
  K       kill a running agent (also stops queued and detached runs)
  R       resume an orphaned run's agent session in its original worktree
          (adapter support required, see |hangar-adapters|)
  s       spawn a new run (prompts for input)
  o       cycle sort order: recent (default) -> status -> cost. Groups
          sort by their newest member and stay together
  f       toggle hiding merged runs
  r       refresh the files column
  q/<Esc> close

5. CONFIGURATION                                               *hangar-config*

>lua
    require("hangar").setup({
      default_permission = nil,  -- "yolo"|"safe"|nil (nil: explicit flag
                                 -- required per spawn)
      merge = "squash",          -- "squash"|"ff"|"merge"
      adapter = "claude_code",   -- default agent CLI
      model = nil,               -- default model for claude_code spawns
      adapters = {               -- per-adapter overrides (all optional)
        -- codex = { cmd = "/path/to/codex", model = "gpt-5.3-codex" },
      },
      notify = true,             -- notify on run completion (see below)
      max_concurrent = nil,      -- cap on running agents (see below)
    })
<
`claude_cmd` is a deprecated alias for `adapters.claude_code.cmd`.

notify ~
    When a run finishes as done or failed while the dashboard is closed,
    hangar calls |vim.notify()| with the run id, elapsed time, cost (when
    the adapter reports one), and the error for failures. Set to `false`
    to silence, or to a `function(run)` to route runs to a custom sink
    (the function replaces vim.notify entirely). Notifications are
    always suppressed while the dashboard is open — it already shows the
    change live.

max_concurrent ~
    Caps how many agent processes run at once (counted across all
    repos). Spawns past the cap park with status "queued" (icon ◌, no
    worktree yet) and start oldest-first as running runs finish or are
    killed. Killing a queued run drops it from the queue. Queued runs
    that survive an nvim restart are marked killed, never auto-started.
    nil (the default) means unlimited.

6. LUA API                                                        *hangar-api*

setup({opts})                                                 *hangar.setup()*
    Apply configuration (|hangar-config|). Optional; defaults work.

spawn({prompt}, {opts})                                       *hangar.spawn()*
    Spawn a run. {opts}: `permission_mode` ("bypassPermissions" or
    "acceptEdits"), `model`, `adapter`, `n`. Returns the run, or a list of
    runs when `n` > 1.

status()                                                     *hangar.status()*
    Statusline string like "hangar 2 ● 1 ✓" (running / awaiting review /
    ✗ failed), or "" when idle. Cached; safe to call on every redraw.

status_counts()                                       *hangar.status_counts()*
    Raw `{ running, queued, done, failed }` counts for custom formatting.

version                                                       *hangar.version*
    Installed plugin version as a string, e.g. "0.2.0". Also shown by
    `:checkhealth hangar`.

                                                          *hangar-autocmd*
Every run change fires `User HangarRunUpdate` with `data = { id }` — UIs
and statuslines subscribe to it.

7. ADAPTERS                                                  *hangar-adapters*

An adapter is a module in `lua/hangar/adapters/` with three fields:
`name` (string), `build_cmd(opts) -> argv`, and `parse_line(line) ->
event|nil` normalizing output into `init`/`text`/`tool_use`/`tool_result`/
`result` events. Unknown event types must be ignored.

Shipped adapters and their permission mappings:

  adapter      --yolo                        --safe
  -----------  ----------------------------  ---------------------------
  claude_code  --permission-mode             --permission-mode
               bypassPermissions             acceptEdits (edits only)
  codex        --dangerously-bypass-         --sandbox workspace-write
               approvals-and-sandbox         (sandboxed shell allowed)
  gemini       --approval-mode yolo          --approval-mode auto_edit
  opencode     --auto                        unsupported: spawn fails fast

Safe mode is live-verified end-to-end for claude_code and codex; the
gemini mapping follows the CLI docs but is not live-verified. opencode
has no headless safe mode — without `--auto` it blocks forever on
permission prompts, so hangar rejects the spawn with an error instead.
An adapter can declare such gaps in an optional `unsupported_modes`
table (permission mode -> reason); spawn fails fast with the reason.

Resume support (the dashboard `R` action) is another optional adapter
capability, `build_resume_cmd(opts)`:

  claude_code   claude -p --resume <session_id>     supported
  codex         codex exec resume <thread_id>       supported
  gemini        —                                   not supported
  opencode      —                                   not supported

Sessions are captured from each CLI's stream output; runs spawned by
hangar versions that passed `--no-session-persistence` (claude) or
`--ephemeral` (codex) have no persisted session and fail to resume with
the CLI's own error.

9. PICKERS                                                    *hangar-pickers*

Optional fuzzy pickers over the run registry; the core stays
dependency-free. Actions: <CR> transcript, <C-d> review, <C-e> iterate
with feedback, <C-x> discard.

telescope.nvim: >vim
    :lua require("telescope").load_extension("hangar")
    :Telescope hangar runs
<
fzf-lua: >vim
    :lua require("hangar.pickers.fzf").runs()
<

10. HOW IT WORKS                                            *hangar-internals*

`:Hangar spawn` creates a worktree on branch `hangar/<id>` under
`stdpath("cache")/hangar/worktrees/` — outside your repo, so agents can
never touch your working tree — and runs the agent CLI there headlessly
via |vim.system()|. Output streams into the run registry; UIs update via
the |hangar-autocmd|. A run that finishes with uncommitted changes is
auto-committed so its branch is always mergeable. State persists to
`stdpath("data")/hangar/runs.json`. Runs that were live when Neovim
exited come back as "detached" (◎) while their agent process is still
alive — watch it, kill it, review its output — and flip to "orphaned"
(?) once the process is gone. Orphaned runs stay reviewable and
mergeable, and `R` resumes their agent session in the original worktree
where the adapter supports it.
